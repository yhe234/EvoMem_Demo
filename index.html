EvoRule Harness

Lifelong Harness Adaptation with a Two-Tier Memory of Validated Causal Rules

Abstract

What we propose

We present EvoRule Harness, a plug-and-play framework for lifelong harness adaptation built around a two-tier memory of validated causal rules. Unlike existing memory-based approaches that store undifferentiated experience, EvoRule Harness represents each adaptation as a testable causal rule linking an applicability context to an intervention, together with execution feedback, confidence, and lifespan. When a failure occurs, the resulting reflection is converted into independently traceable atomic patches over Add, Delete, Refine, Split, and Merge, allowing each update to be validated, attributed, and rolled back separately. New or revised rules first enter a volatile tier, where they are re-tested and continuously revalidated as new evidence arrives. Only rules that remain reliable over repeated validation are promoted to stable memory. Crucially, volatile rules can already guide inference, but cannot directly overwrite stable knowledge; when the two tiers prescribe conflicting interventions, stable rules take precedence. Stable memory itself evolves conservatively, with modifications restricted to Merge or Delete after repeated cross-subset failures. EvoRule Harness operates entirely around a frozen backbone and existing harness optimizer, requiring no gradients, weight updates, or task-specific training.

Method

How it works

Two-tier rule memory

Each rule links an applicability context phi to an intervention psi, with execution feedback omega, calibrated confidence c, and lifespan tau:

r = <φ, ψ, ω, c, τ>

The rule base is the disjoint union of a stable tier and a volatile tier:

Et = Etstable  ∪  Etvolatile

Atomic edit operations

Every update is an independently traceable patch over the operation set:

O = { ADD, DELETE, REFINE, SPLIT, MERGE }

Each patch is logged separately with its own provenance, pass/fail outcome, and rollback metadata, enabling precise credit assignment.

Evidence-gated promotion

A volatile rule is promoted to the stable tier only when

ct ≥ θc   and   at ≥ θage

where confidence follows a Beta-Bernoulli posterior with prior strength n0:

α0 = n0 c0,    β0 = n0 (1 − c0),    ct = (α0 + St) / (α0 + β0 + St + Ft)

Promotion is atomic and one-way. Stable memory is never directly modified by volatile edits.

Stable protection

Stable rules may only be modified by Merge or Delete, triggered only after repeated cross-subset underperformance. Direct Refine or Split on stable rules is rejected. Conflicts resolve in favor of the stable tier.

Inference

Given a query, retrieve Top-K rules separately from each tier by cosine similarity, merge candidates, and resolve conflicts in favor of the stable rule.

Results

EvoRule Harness improves existing harness optimizers by up to 35.7% on average, with gains that grow over sequential adaptation rounds.

Quick Start

Get running in minutes

Installation

git clone https://github.com/yhe234/EvoMem.git
cd EvoMem
pip install -e .

Minimal example

python 
from evorule_harness import (
    EvoRuleConfig, EvoRuleEngine, Patch, PatchOperation,
    Rule, SQLiteStore, ValidationEvidence,
)

store = SQLiteStore(":memory:")
engine = EvoRuleEngine(store, config=EvoRuleConfig(
    prior_strength=2.0,        # n0
    promotion_confidence=0.8,  # theta_c
    promotion_age=3,           # theta_age
))

rule = Rule(
    rule_id="contrastive-verify",
    phi="identical retrieved labels and low confidence",
    psi="retrieve counterexamples and ask for comparative verification",
    omega="pending",
    initial_confidence=0.9,
)
patch = Patch(
    patch_id="repair-contrastive",
    operation=PatchOperation.ADD,
    result_rules=(rule,),
    context=rule.phi,
    judge_confidence=0.9,
    provenance={"failure_case": "rare-class-retrieval"},
)

# Round 1: stage + retest on the original failure
engine.update_cycle([patch], 1, [
    ValidationEvidence(patch_id=patch.patch_id, success=True,
                       subset_id="gastro", round_id=1,
                       original_failure_recovered=True)
])

# Rounds 2-3: cross-subset validation
engine.update_cycle([], 2, [ValidationEvidence(
    patch_id=patch.patch_id, success=True,
    subset_id="dermatology", round_id=2)])
engine.update_cycle([], 3, [ValidationEvidence(
    patch_id=patch.patch_id, success=True,
    subset_id="vascular", round_id=3)])

# Round 4: promotion
result = engine.update_cycle([], 4)
print(result["promoted"])                          # [contrastive-verify]
print(store.get_rule("contrastive-verify").tier)   # RuleTier.STABLE
store.close()

Integrations

Plug into any harness

EvoRule Harness is a plug-and-play memory layer: it attaches to a frozen backbone and an existing harness optimizer without modifying either. Working examples live under integrations/:

  • integrations/tthe/ — EvoRule Harness + TTHE
  • integrations/meta_harness/ — EvoRule Harness + Meta-Harness

Adding new integrations is straightforward. The core requirement is to connect EvoRule Harness to three components of the base harness:

P

Proposer

Generates candidate edits or harness updates.

J

Judger

Diagnoses failures and produces reflections.

E

Executor

Applies candidate edits and re-tests them.

EvoRule Harness sits between these three: it converts the judger's reflections into atomic patches, stages them in the volatile tier, and promotes them to the stable tier only after evidence-gated validation. Any base harness exposing these three roles can be integrated via a thin adapter under integrations/.
